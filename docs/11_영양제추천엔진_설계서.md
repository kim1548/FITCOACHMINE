# 11. 영양제 추천 엔진 설계서

> FitCoach에 영양제 **맞춤 추천 + 복용 알림** 기능을 추가하기 위한 설계 문서.
> 벤치마크: 필라이즈(Pillyze) — AI 맞춤 추천 / 부작용 경고 / 복용 알림 / 식단 통합.

---

## 0. 설계 원칙 (가장 중요)

- **ML 학습 아님.** 추천 로직의 본체는 **규칙 기반 매칭**이다. "DB 학습"이 아니라 **기준표(권장섭취량)·성분 DB·규칙 테이블**을 구축하는 일.
- **AI(Ollama gemma3:4b)는 자연어 "추천 이유" 멘트 생성에만 사용.** 추천 판정 자체에는 관여하지 않는다. → 기존 `inbody_ai.py` / `journal_ai.py` 패턴 그대로 재사용.
- **의료행위 아님.** 결과는 "정보 제공"이며 화면·프롬프트에 면책 문구를 명시한다. (기존 AI 프롬프트의 "약 추천 금지" 규칙과 충돌하므로 별도 톤의 프롬프트 필요 — §6 참고)
- 기존 자산 최대 재사용: `users`(프로필), `diet_logs`(영양소), `inbody_logs`(체성분), `ReminderScheduler.jsx`(알림), Ollama 서비스 패턴.

---

## 1. 전체 파이프라인

```
[입력]                          [엔진]                               [출력]
users 프로필         ┐
diet_logs (최근 7일) ┤→  ① 영양소 섭취량 집계
inbody_logs          ┘         ↓
user_health_profile      ② 권장섭취량(RDA) 대비 부족/과다 판정
 (알러지/질환/약/임신/흡연)     ↓
                         ③ 부족 영양소 → 영양제 후보 매칭
                               ↓
                         ④ 안전 필터 (상호작용/금기/알러지)  →  ⚠️ 경고 목록
                               ↓
                         ⑤ 점수화 & 랭킹 (0~100)            →  추천 Top N
                               ↓
                         ⑥ Gemma 자연어 추천 이유 생성       →  ai_comment
```

## 3. 엔진 알고리즘 (규칙 기반)

### ① 섭취량 집계
- `diet_logs`에서 `user_id` + 최근 7일 → 영양소별 **일평균 섭취량** 추정.
- ⚠️ **핵심 한계**: 현재 `diet_logs`는 **칼로리/탄·단·지방(매크로)만** 저장. 비타민·미네랄(미량영양소)이 없다. → §7 결정사항 D1 참고. (MVP는 매크로 + 프로필 휴리스틱으로 시작)

### ② 부족/과다 판정
```
ratio = intake_avg / rda(나이, 성별)
부족  : ratio < 0.7
적정  : 0.7 ≤ ratio ≤ 1.0
과다  : intake_avg > upper_limit
```

### ③ 영양제 후보 매칭
- 부족 영양소 코드 집합 → `supplement_ingredient` 역인덱스 → 해당 성분을 가진 `supplement` 후보 수집.

### ④ 안전 필터 (부작용 경고)
- 후보 영양제의 각 성분에 대해 `interaction_rule`을 사용자 프로필(약/질환/알러지/임신/흡연)과 대조.
  - `severity=금기` 매칭 → **후보에서 제외**
  - `severity=주의` 매칭 → 추천은 유지하되 **경고 메시지 부착**

### ⑤ 점수화 (0~100)
```
score = Σ_영양소 ( 부족도 × 함량커버리지 × 영양소가중치 )
        − 과다페널티
        − 주의감점
부족도        = clamp(1 − ratio, 0, 1)         # 더 부족할수록 ↑
함량커버리지   = min(영양제함량 / (rda − intake), 1)  # 부족분을 얼마나 메우나
영양소가중치   = 목표(goal) 기반 (예: 벌크업→단백질/아연 ↑, 다이어트→비타민D/오메가3 ↑)
```
- 최종 0~100 정규화 후 내림차순 정렬 → Top N(기본 5).

### ⑥ AI 추천 이유 생성
- Top N 각각에 대해 Gemma 호출 → "왜 추천하는지" 1~2문장. (§6)

## 4. API 설계 (신규 라우터 `supplement.py`)

> 기존 `main.py`의 `app.include_router(...)` 패턴에 동일 등록:
> `app.include_router(supplement.router, prefix="/api/v1/supplement", tags=["supplement"])`

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/profile` | 건강 프로필 조회 |
| PUT | `/profile` | 건강 프로필 저장/수정 |
| POST | `/recommend` | 추천 실행 → 결과 캐시. AI 코멘트는 `BackgroundTasks` |
| GET | `/recommendations` | 캐시된 추천 목록 조회 (레이더 차트 데이터 포함) |
| GET | `/{supplement_id}` | 영양제 상세 (성분·경고) |
| POST | `/intake` | 복용 체크 (taken/skipped) |
| GET | `/intake/calendar` | 월별 복용 기록 (streak 계산) |
| GET | `/reminders` | 알림 목록 |
| POST/PUT/DELETE | `/reminders` | 알림 CRUD |

## 5. AI 서비스 `supplement_ai.py` (inbody_ai.py 패턴 복제)

- 진입점: `generate_and_save_reco_comment(reco_id)` 단일 함수 (inbody_ai와 동일 구조).
- `_call_gemma()` 호출 옵션(`keep_alive`, `num_predict`, 이모지 제거 정규식) 그대로 재사용.
- `BackgroundTasks`로 `/recommend` 직후 비동기 실행 → 결과를 `supplement_recommendation.ai_comment`에 캐시.

### 프롬프트 골격 (예)
```
당신은 영양 정보 도우미입니다. 아래 사용자에게 이 영양제를 추천하는 이유를
짧고 친근한 한국어로 설명하세요.
[사용자] 목표: {goal} / 부족 추정 영양소: {부족목록}
[영양제] {name} — 주성분 {성분}
[작성 규칙]
- 2문장, 80자 이내
- 부족 영양소와의 연결을 한 가지만 콕 짚기
- 마크다운·이모지·따옴표 금지
- "진단·치료" 단정 금지, "도움이 될 수 있어요" 톤
- 끝에 의학적 판단은 전문가 상담 권유 한 마디
```
> ⚠️ 기존 inbody/journal 프롬프트의 `"약 추천 금지"` 규칙과 목적이 상충 → 이 서비스는 **별도 톤(정보 제공 + 면책)** 으로 작성.

## 6. 프론트엔드

### 신규 페이지 `SupplementPage.jsx` (`/supplement`)
- **부족 영양소 레이더 차트** — 이미 의존성에 있는 **Recharts** 사용.
- **추천 카드 리스트** — 점수·성분·경고배지·AI 이유. 커뮤니티/저널의 매거진 디자인 토큰(`bg-paper`, `accent-red`, `font-mono`) 재사용.
- **복용 타임라인 + streak 캘린더** — 연속 복용일수 표시.
- 라우트 등록(`App.jsx`) + `BottomNav` 항목 추가.

### 건강 프로필 입력
- `Settings.jsx` 또는 온보딩에 알러지/질환/약/임신/흡연 입력 폼.

### 알림 — `ReminderScheduler.jsx` 확장
- 현재 foreground 스케줄러가 `localStorage(notif_times)` 기반으로 운동/식사 알림만 처리.
- 영양제 알림을 추가: `supplement_reminder`를 서버에서 불러와 동일 `tick()` 루프에 합류시키거나, MVP는 localStorage에 영양제 시간 추가.
- (정식: 서버 스케줄러 + Web Push — 주석에 이미 명시된 장기 방향)

## 7. 데이터 확보 방안 (학습 X, 시드 O)

| 데이터 | 규모(MVP) | 출처 |
|---|---|---|
| `nutrient_rda` | ~20 영양소 × 연령/성별 밴드 | **KDRIs 한국인 영양소 섭취기준** (보건복지부·한국영양학회 공개표) → CSV 시드 |
| `supplement` + `supplement_ingredient` | 50~100개 샘플 | **식약처 건강기능식품 OpenAPI**(공공데이터포털) 또는 수동 시드 |
| `interaction_rule` | ~20 대표 규칙 | 수동 작성 (와파린×오메가3, 신장질환×칼륨 등) |

> 2~3만개 전체 DB는 **불필요**. 샘플로 동작·시연 충분. 시드는 `backend/app/data/`(이미 gitignore된 데이터 폴더) 또는 별도 seed 스크립트로.

## 8. 단계별 구현 계획 (Phasing)

- **Phase 1 — MVP (추천 + 표시)**
  1. 모델 4종(static) + 2종(profile, recommendation) 추가, 시드 적재
  2. 엔진: 매크로 + 프로필 휴리스틱 기반 부족 판정 → 매칭 → 안전필터 → 점수
  3. `supplement.py` 라우터 (`/profile`, `/recommend`, `/recommendations`)
  4. `supplement_ai.py` (Gemma 추천 이유)
  5. `SupplementPage.jsx` (레이더 차트 + 추천 카드) + 라우트/네비
- **Phase 2 — 복용 관리**
  6. `supplement_intake_log` + 복용 체크 + streak 캘린더
  7. 미량영양소 정밀화(식품-영양 매핑 DB 연동 — D1 결정 따라)
- **Phase 3 — 알림 고도화**
  8. `supplement_reminder` CRUD + ReminderScheduler 통합
  9. (장기) 서버 스케줄러 + Web Push

## 9. 결정 필요사항 (구현 전 합의)

- **D1. 미량영양소 데이터 부재** — `diet_logs`엔 매크로만 있어 비타민/미네랄 부족 판정 근거가 없음. 선택:
  - (a) 식품→영양소 매핑 DB를 붙여 미량영양소까지 산출 (정확·작업량 큼)
  - (b) 프로필/목표/생활습관 기반 휴리스틱 추천 (간단·근거 약함) ← MVP 추천
  - (c) 사용자가 부족 의심 영양소 직접 선택
- **D2. 면책·범위** — 영양제 추천의 의료 책임 경계. 면책 문구 노출 위치·강도, AI 프롬프트 톤 확정.
- **D3. 영양제 DB 소스** — 식약처 OpenAPI 키 발급 vs 수동 시드 50개. (시연 목적이면 수동이 빠름)
- **D4. 알림 범위** — MVP는 foreground(localStorage) 유지 vs 서버 스케줄 도입.
