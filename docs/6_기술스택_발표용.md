# FitCoach 기술 스택 설명서 (발표용)

> 각 기술을 **무엇(What) · 어떻게(How) · 왜(Why)** 로 정리. 발표 시 "왜 이걸 썼나"를 설명할 수 있게 구성.
> ※ 음식 분류 모델(EfficientNet)은 본인 담당 아니므로 **제외**.

## 0. 전체 아키텍처 — "왜 프로세스를 4개로 나눴나" (핵심)

```
[프론트 :5173]  ──/api──▶  [메인 백엔드 :8001 (FastAPI)]
   (React/Vite)                 │
                                ├──HTTP──▶ [영상 분석 사이드카 :8003 (Python 3.10)]  ← 폼체크
                                └──HTTP──▶ [Ollama :11434 (gemma3:4b)]              ← AI 총평
```

- **무엇**: 메인 백엔드(8001) + 영상 분석 사이드카(8003) + LLM(11434) + 프론트(5173), 4개 프로세스 분리.
- **어떻게**: 메인 백엔드가 폼체크 요청을 사이드카로 HTTP 위임(`VIDEO_SERVICE_URL`), AI 총평은 Ollama로 위임.
- **왜 (가장 중요한 설계 결정)**: 폼체크 AI(MediaPipe·scikit-learn)는 **Python 3.10 + 특정 버전**이 필수인데(아래 참고), 메인 백엔드의 최신 스택과 **의존성이 충돌**한다. 그래서 폼체크만 **별도 Python 3.10 환경(.venv310)** 으로 격리하고 HTTP로 통신 → **버전 충돌 회피 + 장애 격리**(사이드카가 죽어도 본 서비스는 동작).

## 1. 백엔드

### FastAPI (웹 프레임워크)
- **무엇**: Python 비동기 웹 프레임워크. REST API 서버.
- **어떻게**: `/api/v1/...` 엔드포인트(auth·routine·diet·body·journal·community·report 등), 의존성 주입으로 DB 세션·인증 처리.
- **왜**: ① **자동 API 문서**(Swagger `/docs`), ② **Pydantic 기반 입력 검증**으로 타입 안전, ③ 비동기로 외부 호출(Ollama·사이드카) 대기 효율적, ④ Flask보다 현대적·타입힌트 친화.

### SQLAlchemy + SQLite (ORM + DB)
- **무엇**: ORM(객체-관계 매핑) + 파일 기반 관계형 DB.
- **어떻게**: 모델을 Python 클래스로 정의(`User`, `DietLog`, `CommunityPost`…), `Base.metadata.create_all`로 테이블 자동 생성, 컬럼 추가 시 시작 시점에 `ALTER TABLE` 마이그레이션.
- **왜 SQLite**: 별도 DB 서버 설치 불필요(파일 하나 `test.db`) → **프로토타입·시연·이식성**에 최적. (단점: 고동시성엔 부적합 — 프로젝트 규모엔 충분)
- **왜 ORM**: SQL 직접 작성 대신 객체로 다뤄 생산성↑, DB 교체 용이.

### 인증 — JWT (python-jose) + bcrypt(직접 호출)
- **무엇**: 토큰 기반 무상태 인증 + 비밀번호 해시.
- **어떻게**: 로그인 시 JWT 발급 → 프론트가 `Authorization: Bearer` 헤더로 전송 → 서버가 검증. 비밀번호는 `bcrypt` 라이브러리를 **직접 호출**해 해시로 저장(passlib 미사용 — bcrypt 4+ 호환 문제로 단순화).
- **왜**: 세션 저장소 없이 **무상태 확장** 가능, 비밀번호 평문 저장 금지(보안).

### Pydantic (데이터 검증)
- **무엇/어떻게/왜**: 요청 본문을 스키마로 검증(타입·필수값) → 잘못된 입력은 422로 자동 차단. 안정성·문서화 자동.

## 2. 폼체크(자세 분석) AI 파이프라인 — **발표 하이라이트**

> 영상 1편 → 자세를 프레임별로 분석 → **5축 진단**(안정성·가동범위·동작품질·자세·코어) 리포트.
> 처리 위치: 사이드카(:8003), 파일 `video_service.py` / `pose_pipeline.py`.

### ⓪ 기반 연구 (원작 출처) — *발표 시 반드시 언급*
- **원작**: PSLeon24(고영민), GitHub `AI_Exercise_Pose_Feedback`
  (https://github.com/PSLeon24/AI_Exercise_Pose_Feedback)
- **논문**: IEEE Access 2024, *"Real-time AI posture correction for powerlifting exercises using YOLOv5 and MediaPipe"*
- **원작 구성**: **YOLOv5 + MediaPipe + Random Forest**, 파워리프팅 **3대 운동**(벤치프레스·스쿼트·데드리프트) 자세 교정.
- **원작 정확도 (Random Forest, 측정값)**:

  | 운동 | Accuracy | Precision | Recall | F1 |
  |---|---|---|---|---|
  | 스쿼트 | **0.989** | 0.989 | 0.989 | 0.989 |
  | 벤치프레스 | **0.961** | 0.963 | 0.961 | 0.961 |
  | 데드리프트 | **0.947** | 0.949 | 0.947 | 0.948 |

  (논문 결론: 자세 분류에서 **머신러닝(RF)이 딥러닝보다 우수** → 원작·FitCoach 모두 RF 채택)
- **내가 한 것 (핵심 기여)**: 이 모델을 **분석**한 뒤, 원작에 **없던 점수 기반(score-based) 평가 로직을 직접 설계·구현**했습니다(자세를 정상/오류가 아닌 **정량 5축 점수**로 환산). 그리고 ① **이 점수 로직을 토대로 지원 운동을 18종으로 확장**, ② **FitCoach 서비스에 통합**(FastAPI 사이드카·웹 연동), ③ **실시간 진행률·운동 종류 검증 게이트** 등 서비스 레이어를 덧붙였습니다.
- **왜 이 연구를 골랐나**: 파워리프팅 자세 교정에 대해 **검증된(IEEE 게재) 실시간 파이프라인**이라 신뢰할 수 있는 토대였고, YOLO+MediaPipe+트리 기반 분류라는 **가볍게 재현·확장 가능한** 구조였기 때문.

#### ⚠️ 지원 운동 18종 = 두 갈래 (정직하게 구분)
| 구분 | 운동 | 방식 | 정확도 |
|---|---|---|---|
| **3대 운동** (원작 학습 모델) | 벤치프레스·스쿼트·데드리프트 | `rf_yolo` — **학습된 Random Forest(.pkl)** | 위 표(94.7~98.9%) |
| **추가 15종** (본인 확장) | 바벨컬·플랭크·런지·오버헤드프레스·바벨로우·인클라인벤치·랫풀다운·사이드레터럴·머신플라이·스모데드·프론트레이즈·클로즈그립벤치·라잉트라이셉스·크런치·레그레이즈 | `rule_based` — **관절 각도 규칙 + 점수 로직** | **없음(측정 불가)** |

- **추가 15종에 정확도 수치를 붙이지 말 것.** 학습한 모델이 아니라 **규칙 기반(생체역학 각도 임계값 + 상태머신)** 이라, 라벨링된 검증셋이 없어 **분류 정확도라는 지표 자체가 성립하지 않음.**
- **왜 학습 안 했나 (질문 대비)**: 지도학습은 **라벨링된 데이터셋이 필수**인데, ① 추가 운동용 공개 데이터셋이 **없고**, ② 직접 구축(운동×다각도×정상/오류 촬영·라벨링)은 **학기 범위를 벗어남**, ③ 원작 `.pkl`은 3대 운동 특화라 **재사용 불가**. → 많은 운동은 각도 기준이 명확해 **규칙 기반으로 충분**하므로 의식적으로 택한 결정.
- **확장성(마무리)**: 동일 파이프라인에 **데이터만 모이면 학습 모델로 교체 가능**하게 설계 → 구조적으로 학습 기반까지 확장 여지.

> ⚠️ 발표 정직성 포인트: "**3대 운동은 PSLeon24의 IEEE 2024 학습 모델(94~99%)을 쓰고, 제가 추가한 운동들은 학습 데이터가 없어 관절 각도 규칙 + 직접 만든 점수 로직으로 판정합니다. 규칙 기반이라 별도 정확도 수치는 제시하지 않습니다.**"

### ① YOLO (사람/바 크롭)
- **무엇**: 객체 탐지 모델(YOLOv8/YOLOv5). 영상에서 **사람·바벨 영역을 검출해 크롭**.
- **어떻게**: 프레임에서 대상 박스를 찾아 잘라낸 뒤 포즈 추정에 넘김.
- **왜**: 배경·여러 인물 노이즈를 제거하고 **대상에 집중** → 포즈 추정 정확도↑, 연산 안정화.

### ② MediaPipe Pose (자세 추정)
- **무엇**: 구글의 실시간 포즈 추정. 사람 1명의 **관절 키포인트(33개 랜드마크)** 추출.
- **어떻게**: 크롭된 프레임마다 관절 좌표를 뽑아 각도·가동범위·좌우 대칭 등 **특징(feature)** 계산.
- **왜**: **별도 학습 없이** 바로 쓰는 강력한 포즈 모델. (클래식 `solutions` API 사용 — 그래서 `mediapipe==0.10.14` 고정: 최신 빌드엔 이 API가 빠져 있음)

### ③-A 3대 운동 — scikit-learn 학습 모델(.pkl), *원작의 Random Forest*
- **무엇**: 3대 운동 전용 **학습된 분류 모델** — `benchpress.pkl`·`squat.pkl`·`deadlift.pkl` (`models/` 폴더에 **이 3개뿐**). 원작과 동일한 **Random Forest**.
- **어떻게**: MediaPipe 자세 특징을 입력해 **자세 정상/오류**를 판정.
- **왜 Random Forest**: 관절 각도 같은 **표 형식(tabular) 특징**에 강하고, 적은 데이터로도 잘 학습되며 **과적합에 견고**(딥러닝 대비 가볍고 해석 쉬움 — 원작도 동일).
- **왜 버전 고정**: `.pkl`은 **학습 당시 버전(1.3.x)** 으로 직렬화 → `scikit-learn==1.3.2`, `numpy==1.26.4`로 맞춰야 예측이 안 깨짐. ← **Python 3.10 사이드카가 필요한 이유.**

### ③-B 추가 15종 — 규칙 기반(rule-based) 판정, *본인 구현*
- **무엇**: 학습 모델 없이 **관절 각도 임계값 + 운동별 상태머신**으로 자세를 판정(예: OHP 팔꿈치 락아웃, 플랭크 척추 중립).
- **어떻게**: MediaPipe 좌표에서 각도를 계산해 규칙 위반을 감점 → 점수화.
- **왜**: 추가 운동용 **라벨링 데이터셋이 없어** 지도학습 불가. 많은 운동은 각도 기준이 명확해 규칙 기반으로 충분 → **데이터 없이 빠르게 확장**. (정확도 수치는 없음 — 학습 모델이 아님)

### ④ 5축 점수 산출 (③-A·③-B 공통, *본인의 핵심 기여*)
- **무엇/어떻게**: 프레임별 판정을 모아 **안정성·가동범위·동작품질·자세·코어** 5개 지표의 **정량 점수**로 환산해 리포트. ← 원작에 없던 **점수 기반 로직**.
- **왜**: 단일 "맞다/틀리다"가 아니라 **다축 정량 피드백**으로 무엇을 고쳐야 하는지 제시.

> 발표 포인트: "**크롭(YOLO) → 포즈(MediaPipe) → [3대: RF 학습 모델 / 추가: 규칙 기반] → 5축 점수 리포트**" 구조, **점수 로직은 본인 기여**, **버전 충돌로 Python 3.10 사이드카 분리**.

## 3. AI 총평 — Ollama + gemma3:4b (로컬 LLM)

- **무엇**: 로컬에서 도는 경량 LLM(gemma3:4b)로 **자연어 코칭 총평** 생성(인바디 코멘트·주간 리포트·저널).
- **어떻게**: 백엔드가 기록 데이터를 프롬프트로 만들어 `http://localhost:11434/api/generate`에 요청 → 응답 텍스트를 저장/표시.
- **왜 로컬 LLM**: ① **API 키·비용 없음**, ② **데이터가 외부로 안 나감(프라이버시)**, ③ 인터넷 없이도 동작, ④ 4B 모델이라 일반 PC(CPU)에서 구동 가능. (첫 호출은 모델 로딩으로 수십 초 — 발표 시 미리 1회 호출해 워밍업 권장)

## 4. 프론트엔드

### React 19 + Vite
- **무엇**: 컴포넌트 기반 UI 라이브러리 + 차세대 빌드 도구.
- **어떻게**: 페이지/컴포넌트 분리, React Router로 라우팅, 상태는 Context(Auth)·로컬 state.
- **왜 Vite**: 매우 빠른 **HMR(저장 즉시 반영)** 개발 경험, 가벼운 빌드. CRA 대비 빠름.

### TailwindCSS v4
- **무엇**: 유틸리티-퍼스트 CSS.
- **어떻게**: 디자인 토큰(`@theme`)으로 색·폰트 정의, 클래스로 스타일링("Editorial Magazine" 다크 톤).
- **왜**: 별도 CSS 파일 없이 **빠르고 일관된** 스타일링, 디자인 시스템 유지 쉬움.

### Recharts
- **무엇/어떻게/왜**: React용 선언적 차트. **체성분 추이 그래프**(체중·골격근·체지방)를 데이터만 넘기면 렌더 → 시각화 간편.

### PWA (vite-plugin-pwa)
- **무엇**: 웹앱을 **모바일 홈 화면에 설치**(앱처럼 전체화면 실행).
- **어떻게**: manifest(앱 이름·아이콘)·service worker(앱 셸 캐시) 자동 생성, "홈 화면에 추가"로 설치.
- **왜**: **앱스토어 없이** 앱 경험 제공, 오프라인 셸·아이콘. 정식 출시 시 Web Push로 확장 가능.

### 반응형 비례 스케일 (rem + viewport 연동 루트 폰트)
- **무엇/어떻게**: 고정 px를 rem으로 전환하고 루트 글꼴을 `clamp(16px, 1.111vw, 24px)`로 화면폭에 비례시킴.
- **왜**: **노트북에서 보던 비율을 모니터에서도 동일**하게 재현(글자·여백·요소가 통째로 비례 확대). 큰 모니터 여백 과다 해소.
- **추가**: 저해상도(1x) 모니터에서 1px 선이 진해 보이는 문제를 **DPI 미디어쿼리**로 톤다운(노트북 영향 없음).

## 5. 모바일 테스트 / 개발 인프라

### Cloudflare 터널 (cloudflared)
- **무엇/어떻게**: 로컬(5173)을 임시 **HTTPS 공개 주소**로 터널링 → 폰에서 접속.
- **왜**: PWA 설치·카메라(`getUserMedia`)·알림은 **HTTPS에서만** 동작 → 로컬 IP(http)로는 불가. 터널로 HTTPS 확보.
- **주소 자동 기록/갱신**: `start-tunnel.ps1`이 발급 주소를 `frontend/public/app-link.txt`에 기록 → 앱의 **SET → Get the app**이 그 파일을 주기적으로 읽어 표시. `tunnel-keepalive.ps1`은 터널이 죽으면(530 등) **자동 재발급**해 주소를 계속 살려 둔다(바탕화면 런처 `start_fiteating.bat`에 포함). ※ 임시 터널이라 재발급 시 주소는 바뀜(고정 주소는 Named Tunnel 필요).

## 6. 발표 예상 질문 & 답변 (Q&A)

**Q. 왜 백엔드를 두 개(8001·8003)로 나눴나요?**
A. 폼체크 AI는 `mediapipe`·`scikit-learn`이 **Python 3.10 + 특정 버전**을 요구하는데 메인 백엔드 스택과 충돌해서, **별도 3.10 환경으로 격리**하고 HTTP로 통신했습니다. 의존성 충돌을 피하고, 사이드카 장애가 본 서비스로 번지지 않게 했습니다.

**Q. 왜 외부 GPT API가 아니라 로컬 Ollama인가요?**
A. **비용 없음·데이터 외부 유출 없음·오프라인 동작** 때문입니다. gemma3:4b는 가벼워 일반 PC에서 돌아갑니다.

**Q. YOLO와 MediaPipe를 둘 다 쓴 이유는?**
A. YOLO로 **대상(사람·바)을 크롭**해 노이즈를 줄인 뒤, MediaPipe로 **관절을 정확히 추정**합니다. 역할이 다릅니다(검출 vs 포즈).

**Q. 자세 분석 모델은 직접 다 만든 건가요?**
A. 핵심 파이프라인은 **PSLeon24의 IEEE Access 2024 연구**(YOLOv5+MediaPipe+Random Forest, 파워리프팅 3대 운동)를 **기반**으로 했습니다. 저는 원작에 **없던 점수 기반 로직을 직접 만들고**, 그걸 토대로 **지원 운동을 18종으로 확장**, **FastAPI 사이드카로 서비스화**했습니다.

**Q. 추가한 운동들 정확도는 얼마인가요?**
A. **정확도 수치는 없습니다.** 3대 운동(벤치·스쿼트·데드)만 원작의 **학습된 RF 모델**(94.7~98.9%)을 쓰고, 제가 추가한 15종은 **학습 모델이 아니라 관절 각도 규칙 + 점수 로직**으로 판정합니다. 라벨링된 검증셋이 없어 **분류 정확도라는 지표 자체가 성립하지 않습니다.** (없는 수치를 만들지 않는 게 정직한 답)

**Q. 추가 운동은 왜 학습을 안 했나요?**
A. 지도학습엔 **라벨링된 데이터셋이 필수**인데 ① 추가 운동용 공개 데이터셋이 없고, ② 직접 구축(운동×다각도×정상/오류 촬영·라벨링)은 학기 범위를 벗어나며, ③ 원작 모델은 3대 운동 특화라 재사용이 안 됩니다. 많은 운동은 각도 기준이 명확해 **규칙 기반으로 충분**했습니다. 다만 동일 파이프라인에 **데이터만 모이면 학습 모델로 교체 가능**하게 설계했습니다.

**Q. 왜 SQLite인가요? 실서비스엔 약하지 않나요?**
A. 프로토타입/시연엔 **설치 0·이식성**이 최적이라 선택했습니다. ORM(SQLAlchemy)을 써서 추후 PostgreSQL 등으로 **교체가 쉽게** 설계했습니다.

**Q. 자세 점수는 어떻게 나오나요?**
A. MediaPipe 관절에서 각도·가동범위 등 **특징을 뽑아**, 3대 운동은 **학습된 RF 모델(.pkl)**, 추가 운동은 **각도 규칙**으로 정상/오류를 판정한 뒤, 공통으로 **5축 점수 로직**(본인 구현)으로 환산합니다.

**Q. 모바일은 어떻게 보여줬나요?**
A. **PWA**로 홈 화면 설치 + **Cloudflare 터널(HTTPS)** 로 실제 폰에서 카메라·알림까지 시연했습니다.

**Q. 첫 AI 응답이 느린데요?**
A. LLM/모델 **최초 로딩** 때문입니다. 발표 전 1회 호출로 **워밍업**해두면 빠릅니다.

| React+Vite | 컴포넌트 UI + 빠른 개발 |
| Tailwind | 빠르고 일관된 디자인 시스템 |
| Recharts | 체성분 추이 시각화 |
| PWA | 앱스토어 없이 앱 경험 |
| 반응형 rem/clamp | 어느 화면에서도 같은 비율 |
| Cloudflare 터널 | HTTPS로 폰 시연(카메라·알림) |
